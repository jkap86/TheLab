Manager tool · above the column headings · three seatings

Filter leagues by who's in them

Owns a player, shares a league with a manager — as a row of its own between the plate and the heading rail, not in the filters dialog. That placement settles three things at once and leaves one real question: how much of the list it is allowed to cover.

The slot, and what it costs to sit in it

Read first

Out of the dialog, three problems disappear. The shared modal never learns about a manager, so the trades board keeps a filter set it can fully use. There is no draft to protect, so the row commits live — type, watch the count move. And the state lives outside LeagueFilters entirely, which is where it wanted to be anyway.

What it buys instead is a bill. This row lands inside the pinned header, so its height is league rows covered on every tab, on every screen, forever — the currency this card has already been through two rounds of. Seating the filters key flush in the plate's corner returned 20px of list; the padding trade around it returned 8 more. A row that costs 36px spends both of those and then some. So each option below is priced at rest, with nothing selected, because that is the state it is in almost all the time.

A person is not a rule. Every filter in the dialog is a key, a comparison and a number — qb+sf ≥ 2. A name has nothing to compare against, and there are several hundred of them. So all three options are the same control: a search that leaves tokens behind. What differs is how it rests when you are not using it.
A

An open search rail, spanning the list

A milled slot the full width of the rows below it, permanently open. Tokens sit inside it as they are added; results drop over the list. Nothing to press first — the control is the field.

Why it fits

Nothing announces a search like a search box. It is the only one of the three a reader finds without being curious, it is one click to a first result, and the recessed material is honest — you type into it, so it is a slot rather than a key. Spanning the rows it reads as belonging to the list, the same argument that made the heading rail full width.

What it costs

The most expensive rest state of the three, and it never gets cheaper — an empty field is the same height as a full one. It also puts a permanent second inset band directly above the heading rail, so the header reads as three stacked bars before a single league appears.

B

A key at the left, tokens trailing it

One raised key — Who's in it, badged when it narrows — with the chosen names laid out beside it on the same line. Pressing floats the search over the list. The line is nearly empty until it is used, and it says exactly what is set when it is.

Why it fits

It is the app's own grammar for this: a raised key you press, a floating panel over what it narrows, one open at a time, Escape closing the innermost thing up. The tokens make the selection readable without opening anything — the same debt the filters key pays with its badge and the plate pays with its scope line. And the line carries several names without growing, which is the one thing a collapsed row can't do.

What it costs

A key labelled Who's in it is not self-evidently a search until pressed, so it is the least discoverable of the three. It also puts a third badge-bearing control on one screen — the Filters key below the plate, the ADP block in the app bar, and now this — which is a lot of parts each claiming a small cyan count.

C

An upper storey milled into the heading rail

Not a row above the rail — the top of the rail. One billet, two storeys: the subject line cut into the lit face above, the heading channels below it, one wall and one shadow for both. It is "above the headings" without being a second part.

Why it fits

Cheapest of the three, because a separate part costs more than its own contents: its wall, its drop shadow, and the clearance holding its lit face off the rail's lit face — the exact 20px the filters key gave back by seating flush. One billet pays that once. It also says something true: both storeys are the list's own header, one naming its columns and one naming its population.

What it costs

ColumnsBar is shared by all three tabs and knows nothing about filters today, so it grows a slot and a reason to care. The rail is also drawn only when there are rows to head — so on "no leagues match these filters" the control that would widen the selection disappears with it, and it has to be exempted from that rule.

True of all three

It commits live

No dialog means no draft to protect, so the count moves as you type. The per-name counts are each name's own total rather than what it would leave beside the rest — the honest reading when the list behind is moving.

One search, two kinds of answer

Players and leaguemates in one field, grouped in the results. They are the same question — who is in this league — and two fields would make a reader choose which one they meant before typing a name that only exists in one of them.

The state sits beside the league filters

Its own type in the manager layout's provider, reset per manager by the same subtree key. Narrowing runs in useFilteredLeagues, after the shared predicate, where rosters and members are in hand.

The lists load on open

The players and leaguemates payloads are the other two tabs' resources, off a cache shared per manager — so anyone who has visited either pays nothing, and a cold Leagues tab fetches only once the control is opened.

all and any are both real

Rules narrow on an attribute, so they all AND. These are subjects, and "Bijan or Chase" is asked as often as "both" — the same case the trades selection makes. Default all, as it does.

It narrows all three tabs

Which is the point: Players then answers "who else do I own alongside Bijan", Leaguemates "who am I in those leagues with". Expect the filtered player's own share to read 19 of 19 — correct, and worth a note rather than a fix.

Chosen: C — and here is what it took

C is built. The rail is one billet with two storeys; the subject filter is a pure module (features/manager/subjects.ts, 26 tests) narrowing in useFilteredLeagues after the shared predicate, with its own provider beside the league filters. Three things only showed up once it was rendered: the face's cyan hairline was stranded mid-part and had to travel with the chamfer to the top storey; the storey overflowed the billet at 390px and now wraps; and swapping in a storey-only rail when nothing matched remounted the control, closing the search panel on exactly the press that most needs undoing — so the heading storey is what is conditional, never the rail.

The original reasoning

B, the key with trailing tokens. It is the app's existing grammar with nothing invented, it is the cheapest thing that survives an empty list, and it touches no shared component. The 26px it costs is a row of the list you get back the moment nothing is selected — which is most of the time.

C is the better idea and the riskier build. Folding the control into the rail is the only option that adds no part at all, and two storeys of one billet is the most honest thing to draw. It costs a shared component learning about filters, and an exemption so the control doesn't vanish exactly when a reader has narrowed to nothing. Worth doing if the header's height is the binding constraint.

A only if discovery is the worry. An open field is the one thing nobody has to be told about — but it charges the full price on every screen, every tab, whether or not it is ever used, and this header has spent two rounds buying that height back.

  1. Add it in LeaguesViewLayout, not per tab — the same place the filters key and the ADP trigger are wired, so all three tabs get it once.
  2. Pass it into ManagerHeader as a node beside columns, so the pinned card keeps owning its own stacking and the gap under it.
  3. Narrow in useFilteredLeagues, after matchesFilters, so features/shared stays free of anything the trades board can't use.
  4. Add the subject to the scope line — filterSummary's job, extended: the plate already names what the record is counted over, and this is now part of it.
