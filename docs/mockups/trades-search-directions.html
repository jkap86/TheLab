Trades board · the omnibox, settled · four ways to ask which way

Nabers moved. The board won't say who sold him.

The search finds every trade an asset appears in, which is the right default and half an answer: “did jkap sell Nabers” and “did jkap buy Nabers” are the same query today. Four ways to put a direction on the selection, all seated in the omnibox you picked.

One thing decides the shape of all four. A direction is a fact about a pair, not about a token. Every trade with Nabers in it has somebody giving him and somebody getting him, so “received” on its own narrows nothing — it only means something once there is a manager for it to be relative to. Every option below is a different answer to where that pairing is written down.

The database already knows, and one column has never been read

Read first

Sleeper stores both halves of every move and the sync has been writing both since the first migration. adds is player → the roster that received him, and the board's filter reads its keys — which is exactly why the filter is directionless: a key is present whichever way the player went. drops is the mirror, player → the roster that gave him, and it is written by manager/persist, stored on every trade, and read by nothing in this app.

assemble.ts says “drops is its mirror and carries nothing extra”, and for building a card's sides that is true — what a roster gave is what the others received. This is the case where it does carry something, and the three-way trade is where you can see it: the card declines to draw a give column at three sides because nothing in the sides says which participant an asset came through, and drops says exactly that. The filter can answer a question the card cannot display.

Players

drops->>player is the giving roster, adds->>player the receiving one. Join to rosters.owner_id — the same hop tradedByOwnersSql already makes.

Picks

Each entry in draft_picks carries owner_id and previous_owner_id — who holds it now and who handed it over. Already in the stored JSONB.

Cost

None. Keep t.adds ?| array[…] as the selective predicate so the GIN index still does the narrowing, and add the roster comparison as a filter on the rows it returns.

What it buys

It is unambiguous. The token reads “Malik Nabers · from jkap”, which is the whole question in words — no arrow to decode and no model to learn.

Per-asset, so a selection can mix directions: gave Nabers, got a first is one query rather than two searches and a squint.

Nothing new appears until it can mean something — with no manager selected, the side keys simply aren't drawn.

no new chrome · reads as a sentence

What it costs

A result row grows two keys, and at 390px that pushes it to two lines. Tokens get wider — one per line on a phone.

The direction is relative to “the selected manager”, so with two managers picked the clause has to name one of them, and the token gets longer still.

It cannot ask the question with no manager at all — what went for a 2027 1st is still out of reach. See D.

What it buys

One rule covers every question on this page. Same bay, same side. Manager and player together means he received him; on opposite sides means he gave him; two assets opposed with nobody named means one went for the other.

It is the only option that answers “what did a 2027 first go for”, which is the question the board's own description leads with — and it does it without an account, a manager or a name.

The control looks like the card: two bays over two columns, stacking together at the same width. Nothing to learn that the list below isn't already teaching.

answers the page's headline question

What it costs

The biggest build of the four. The selection stops being three flat lists and becomes two bags with a relation, which changes the query type, the SQL, the facet counts and the URL — where A and B are a field added to what is already there.

160px on a phone against a single field’s 36, and it is chrome whether or not the second bay is used.

A three-way trade makes “the other side” mean “any other side”, which is coherent and still needs saying somewhere.

new selection model · 160px on a phone

True in all four

Decisions that don't depend on the shape

Either way stays the default

The current rule — the filters ask what moved, not who ended up with it — is right for a reader who doesn't yet know which way it went. Direction is something you add, never something you have to clear.

A direction needs two things to be about

Every trade with Nabers has a giver and a getter, so “received” alone matches everything it would have matched anyway. The control appears when the pair exists and not before.

The facet counts are still counted without the selection

Which keeps them stable under a press — but a count next to a name now means “trades this player moved in”, not “trades matching the side you're about to pick”. Worth leaving as is: the alternative re-runs a season-wide aggregate per keystroke.

The card can't always show what the filter matched

On a three-way the give column isn't drawn, because the sides don't say who an asset came through — so a trade matched on “gave” will show the player on somebody else's side with nothing pointing at why. The matched asset should be marked on the card.

It rides the same query string

A directional selection has to survive a reload and a back button like every other filter here — so the token's clause is part of the board's cache key, and two directions of one player are two different boards.

The scope line has to say it

The ledge's summary is what says out loud what the board is showing. “all of 1 manager, 1 player” stops being true the moment a direction is on it — it wants to read “jkap gave Malik Nabers”.

If you want a recommendation

D, and A if the build is too much this week. The question you asked — is this manager giving or receiving this player — is answered by all four. What separates them is the question one row down: what did he get for him, which B cannot ask at all, and what has a 2027 first been going for, which only D can ask. That second one is the sentence this board's own description leads with, and it needs no manager, no account and no name — it is the whole market answering at once.

D's cost is real and it is a build cost, not a legibility one: two bays with a relation is a different selection type from three flat lists, so the query, the SQL, the cache key and the scope line all move together. A is the same feature at a quarter of the work and its token clause (“Malik Nabers · from jkap”) is the one spelling nobody can misread — and it is a strict subset of D, so building A first forecloses nothing.

B is the trap. It is the smallest and it reads perfectly, and the first time someone asks what a player went for it has to be replaced rather than extended.

  1. Say which — a letter, or “A now, D later”.
  2. Read drops — stored on every trade since the first migration, read by nothing. Players resolve through it, picks through draft_picks[].previous_owner_id.
  3. Keep the GIN index doing the work — t.adds ?| array[…] stays the selective predicate; the direction is a filter on the rows it hands back.
